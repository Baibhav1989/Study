1. What is Vlocity EPC?

Enterprise Product Catalog (EPC) is Vlocity's central place to create, manage, and sell products and services. Think of it as one master catalog that your sales team (CPQ), order team, and billing systems all use together.

Simple analogy EPC is like a restaurant menu that the kitchen, waiters, and cashier all share. When the chef adds a new dish once, everyone sees it — no duplicate menus in different departments.

What EPC contains

  • Commercial catalog — what customers see and buy (offers, prices, bundles)
  • Technical catalog — how products are delivered (services, resources, fulfillment)
Enterprise Architecture — Where EPC Sits
Sales Channels (Web, Store, Call Center) → uses EPC
Vlocity CPQ (Configure, Price, Quote) → reads EPC
Vlocity Order Management → fulfills from EPC
Billing & Backend Systems → receives product data

EPC uses a metadata-driven approach — products are defined once as reusable building blocks, then combined into offers, bundles, and promotions.

Companies in telecom, media, and energy use EPC to launch products faster and at lower cost.

  • Single catalog — commercial + technical products in one model
  • Reusable components — attributes, picklists, object types shared across products
  • Simple & complex bundles — sell products alone or as packages

4. TM Forum & SID Model

Vlocity EPC follows the TM Forum Frameworx standard. Products are split into layers — from what marketing sells to what the network delivers.

🛒 Product Offering — What marketing sells (with price)
📋 Product Specification — What the product includes (color, speed, storage)
⚙️ Customer Facing Service (CFS) — Technical service (e.g., broadband internet)
🔧 Resource Facing Service / Physical Resources — Network equipment, IP address, port
Example: Home Internet Package
  • Offer: "Fiber 100 Mbps Plan — $49/month"
  • Product Spec: Router + 100 Mbps speed + SLA
  • Service Spec: Fiber broadband service with authentication
  • Resource Spec: ONT device, IP port, local loop connection

Overrides

Child products inherit attributes from their object type, but you can override values at the product level. You cannot delete inherited attributes — only change their values or picklist defaults.

Example: Download Speed Override Smart Phone object type has Download Speed picklist (25 MB, 50 MB, 100 MB) with default 25 MB. For a premium fiber offer, override the default to 50 MB on that specific product only.

Special Flags (Technical Products)

  • Encrypted — protects PII like SSN or phone numbers
  • Not Assetizable — temporary data (e.g., one-time login password) not stored after order completes

10. Object Types

An object type is a reusable template — like a "class" in programming. Products inherit fields, attributes, and layouts from their object type.

"Is-A" inheritance iPhone is a Smart Phone, which is a Smart Device. Each level adds more specific attributes.
Base Product ← all fields, created once at setup └── Smart Device ← Brand, Size, Storage, Color, OS ├── Smart Phone ← inherits all above └── Smart Wearable ← + Band Type attribute

Layout Management

Layouts control which attributes appear and in what order. In Product Designer, use the General Properties facet with drag-and-drop sections.

13. Attribute Rules & Context Rules

Attribute Rules (Configuration Rules)

Control which attribute options appear based on other selections. Each rule has Conditions (when) and Actions (what happens).

Example: Apple Watch Series 5

Condition: Watch Size = 44mm

Action: Exclude "Silver" from Color picklist

Result: If customer picks 44mm watch, silver is not shown as a color option.

Action TypeWhat It Does
ConstrainInclude or exclude picklist values
AssignSet an attribute to a specific value
DisableShow attribute but prevent editing
RequireForce customer to fill in the attribute
HideRemove from UI (still in data)

Context Rules (Qualification Rules)

Control who can see or buy a product. Used for eligibility — e.g., only customers in certain locations see the 5G plan.

Example: 5G Ultra Plan Qualification rule checks customer location. Only eligible customers see the plan in the "Qualified" tab in Vlocity Cart. Others see it as "Disqualified."

1. What is Vlocity CPQ?

Configure, Price, Quote (CPQ) extends Salesforce to help sales teams build the right order — with correct products, prices, and rules — before it goes to fulfillment.

Simple analogy CPQ is like a smart checkout system. It checks stock (availability), your membership (eligibility), whether items work together (compatibility), and calculates the final price — all before you pay.

What CPQ Does

  • Configure products using attributes in the cart
  • Price orders using price lists, promotions, and pricing plans
  • Apply rules so only valid combinations are sold
  • Convert Opportunity → Quote → Order → Asset
  • Support change orders (MACD) on existing customer assets

5. MACD & Asset-Based Ordering

MACD = Move, Add, Change, Delete. Used when customers already have active services (assets) and want to modify them.

ActionMeaningExample
MoveTransfer service to new location/accountMove internet to new address
AddAdd new product to existing accountAdd Netflix to existing TV plan
ChangeModify existing assetUpgrade 50 Mbps → 100 Mbps
DeleteDisconnect/remove serviceCancel home phone line

Assets can be converted back to Quote or Order for changes. Each asset has an Asset Reference ID used across CPQ and Order Management.

Asset-Based Ordering (ABO) Flow

  1. Open Account → view assets on cards-based VF page (comp-assets-* cards)
  2. Select asset(s) → Change to Quote or Change to Order
  3. Configure changes in Vlocity Cart → Submit → new/updated assets created

Field Mapper

Field Mapper copies custom fields between Quote/Order/Asset during ABO. Add Field Settings records to define which fields map. You can add filters and edit mappings in Setup.

Sub-Actions on change orders Move, Replace, Reassign, and Cancel relate to Change of Plans. Action values on line items: Add, Existing, Change, Disconnect, Suspend, Resume.

Only one version can be active at a time. Deactivate the current version before activating another.

  1. Setup → Flows → open Pricing Rules Flow (deactivate active version first if needed; save as new version)
  2. Drag vlocity_cmt__RuleAction from Apex palette into the flow
  3. Set inputs: ruleType = Pricing, ruleName = exact rule name, doCommit = {!GlobalConstant.True}
  4. Connect the step under the Is Order branch as the last step
  5. Save and activate

Each rule action invokes one rule by name and type. The doCommit flag marks the final rule action in the sequence.

1. Vlocity Async Engine Overview

The Vlocity Async Engine enables long-running processes to execute in the background without hitting Salesforce governor limits. Instead of processing everything in a single synchronous transaction, the engine queues work and processes it asynchronously — ideal for bulk operations, complex Integration Procedures, and multi-step order fulfillment.

Simple analogy Synchronous = ordering at a counter and waiting while they make your food. Async = placing your order via an app, getting a ticket number, and checking back when it's ready (or getting notified).

When to Use Async Processing

ScenarioWhy Async?
Bulk record processing (hundreds/thousands)Avoids CPU & SOQL governor limits
Long-running Integration ProceduresPrevents timeout errors on complex logic
Chained IP calls (IP calling another IP per record)Each iteration gets its own transaction context
EPC maintenance jobs (Compile, Cache)Large catalogs require hours of processing
Order decomposition / orchestration calloutsExternal system responses may be slow

Async Architecture

Vlocity Async Engine — High-Level Flow
1. Caller (OmniScript / Apex / REST) → triggers async process
2. Async Engine creates Async Process record → returns Process ID
3. Background execution (Queueable / Batch) → processes work items
4. Status tracking via Async Process & Jobs → Completed / Failed / In Progress

Key Objects

ObjectAPI NamePurpose
Async Processvlocity_cmt__AsyncProcess__cParent record — tracks the overall process (status, type, start/end time)
Async Process Stepvlocity_cmt__AsyncProcessStep__cChild of Async Process — one logical step (e.g., "Compile Product Hierarchy")
Async Process Jobvlocity_cmt__AsyncProcessJob__cChild of Step — individual batch/unit of work with its own status & error message

Walk-through of the example response above:
  • Process 9876543 (InProgress): Step "Validate" finished with errors — 2 items succeeded, 2 failure groups reported (codes 5001 & 5004). Step "Price" is currently running (3 of 6 items done, no failures yet). Items that failed validation plus retry items were added to the Price step's input.
  • Process 64221481 (Success): Both steps completed successfully — all 6 items passed Validate and all 6 items passed Price. Zero failures across the board.
  • Both processes share referenceId "12324" — this is why the AsyncProcessStatus array has 2 entries. When you query by asyncProcessId instead, you'd get only one.
Querying by referenceId vs asyncProcessId:
• By referenceId — Returns all process runs that share that external Id. Useful when the same business operation triggers multiple async processes (retries, re-runs).
• By asyncProcessId — Returns exactly one record. Use when you need precise status of a specific run.

Polling Pattern — OmniScript or LWC

If you're building a UI that shows async progress to users, use a polling pattern:

// Pseudocode: poll every 5 seconds until terminal status let asyncProcessId = response.asyncProcessId; // from create call let polling = true; while (polling) { await sleep(5000); let status = await callIP('AsyncStatus_GetProcessStatus', { asyncProcessId }); if (status.status === 'Completed') { showSuccess('Process finished: ' + status.completedItems + ' items done'); polling = false; } else if (status.status === 'Failed') { showError('Process failed: ' + status.statusMessage); polling = false; } else { updateProgress(status.completedItems + ' / ' + status.totalItems); } }
Troubleshooting tip: Always drill down to the Job level for the actual error. The parent Process/Step only shows a summary status — the Technical Message on the Job has the stack trace or API error.

4. Delete Async Processes

You can delete or abort async processes that are stuck, no longer needed, or failed and need cleanup.

Method A — Abort Running Batch Jobs (Apex)

// Abort all currently running Vlocity batch jobs vlocity_cmt.VlocityBatchFramework.abortBatchJobs();
// Abort a specific scheduled batch job vlocity_cmt.VlocityBatchFramework.abortScheduledBatchJob();

Method B — Abort via System.abortJob

// For standard Apex async jobs — use the CronTrigger Id, NOT the AsyncApexJob Id List<CronTrigger> jobs = [ SELECT Id FROM CronTrigger WHERE CronJobDetail.JobType = '7' ]; for (CronTrigger job : jobs) { System.abortJob(job.Id); }
Common mistake: Calling System.abortJob with an AsyncApexJob Id throws: "You can't abort scheduled apex jobs by calling System.abortJob with an AsyncApexJob ID. You must use the parent CronTrigger ID."

Method C — Delete Async Process Records

// Delete completed/failed async process records for cleanup List<vlocity_cmt__AsyncProcess__c> oldProcesses = [ SELECT Id FROM vlocity_cmt__AsyncProcess__c WHERE vlocity_cmt__Status__c IN ('Completed', 'Failed') AND CreatedDate < LAST_N_DAYS:30 ]; delete oldProcesses;

Method D — Get Current Running Jobs

// List batch jobs that are not Aborted, Completed, or Failed vlocity_cmt.VlocityBatchFramework.getCurrentBatchJobs();

Returns a list of AsyncApexJob records that are still actively running. Use this to identify stuck jobs before aborting.

Best practice: Before deleting async process records, ensure no downstream logic depends on them (e.g., retry mechanisms, status polling from OmniScripts). Archive the data if audit requirements apply.

1. What is Enterprise Sales Management?

Enterprise Sales Management (ESM) is a Salesforce Communications Cloud solution designed to streamline B2B sales processes for communications service providers (CSPs) selling to large, multisite enterprise and government customers.

Simple analogy Standard CPQ is like ordering a single pizza with custom toppings. ESM is like catering 500 offices across the country — same menu, but you need bulk ordering, location tracking, group pricing, and coordinated delivery for each site.

ESM extends Industries CPQ with prebuilt data models, guided workflows, product models, and templates that handle thousands of line items across multiple locations and subscribers in a single quote.

What ESM Gives You

  • Configurable UI for creating and amending quotes in a centralized location
  • Unified transaction support for large multisite, multi-subscriber quotes
  • Bulk uploads — import locations and subscribers via CSV/XLS
  • Shared catalog with predefined product models (Enterprise Mobile, Business Internet, VPN)
  • Guided flows for browsing products, configuring offers, and viewing quotes
  • Prebuilt templates for auto-generating proposals and contracts (integrates with CLM)
  • Order automation — submit all sub-orders at once or individually over time
